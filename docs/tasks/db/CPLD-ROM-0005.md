# CPLD-ROM-0005 — Retarget ROM image/export and hardware contract to 128 KiB SST39VF010-70

**ID:** `CPLD-ROM-0005`  
**Status:** `RESOLVED`  
**Title:** Retarget ROM image/export and hardware contract to 128 KiB SST39VF010-70

**Description**

Owner decision, 2026-11-21: **use a 128 KiB (1 Mbit, 128K × 8) SST39VF010-70 parallel NOR flash** because the device is convenient to obtain. The first **64 KiB** contains the **existing, approved** Apple IIe and slot firmware layout; the remaining **64 KiB** is **reserved, unused, zero-filled for now**. This explicitly supersedes the earlier 256 KiB target-image requirement in the current ROM mapping and single-image contract. There is **no requirement to use or bank-switch the spare 64 KiB** as part of this ticket.

The emulator is an internal hardware/firmware **development tool**, not a general Apple IIe emulator product: the Apple ROM and the six possible card ROM arrays remain compiled into the emulator, with guarded zero-defaults. The **only CLI option is optional `-w IMAGEFILE`**, which exports **the exact backing from which the emulator runs** as one raw **131072-byte** file ready for programming the selected physical part. Without `-w`, it creates no ROM file. Do **not** reintroduce `--rom`, separate runtime slot-ROM inputs, tagged `CPRM` containers, a ROM packer service, or new bank-selection command-line options.

## 1. Owner-approved, byte-for-byte 128 KiB flash map

**All offsets are absolute byte offsets in the raw `-w` image and the address presented to the SST39VF010-70's A0–A16 lines. No file header or extra metadata is permitted.**

| ROM / flash address (hex, inclusive) | Bytes | Compiled source / expected data | Apple view |
| --- | ---: | --- | --- |
| `00000–00FFF` | 4,096 | Zero-filled; **no slot 0 ROM** | Released expansion owner, no card |
| `01000–01FFF` | 4,096 | `slot1_rom_bin[]` | slot 1 entry / expansion |
| `02000–02FFF` | 4,096 | `slot2_rom_bin[]` | slot 2 entry / expansion |
| `03000–03FFF` | 4,096 | Zero-filled; **no external slot 3 image** | internal Apple slot 3 still supplied by Apple ROM |
| `04000–04FFF` | 4,096 | `slot4_rom_bin[]` | slot 4 entry / expansion |
| `05000–05FFF` | 4,096 | `slot5_rom_bin[]` | slot 5 entry / expansion |
| `06000–06FFF` | 4,096 | `slot6_rom_bin[]` | optional card slot 6 |
| `07000–07FFF` | 4,096 | `slot7_rom_bin[]` | planned ProDOS slot 7 |
| `08000–0FFFF` | 32,768 | **unchanged `apple_rom_bin[]`** (CPU `$8000–$FFFF`) | internal Apple Cx and system ROM |
| `10000–1FFFF` | 65,536 | **Zero fill, reserved** (not currently CPU-visible as ROM) | no assigned bank or feature |

**Invariant:** first 65536 bytes of the new image **must be byte-identical** to the first 65536 bytes generated by the current approved 256 KiB implementation when built from the same compiled inputs. New output is **exactly 131072 bytes (`0x20000`)**, not 64 KiB, 256 KiB, or a padded/mirrored 256 KiB file. There is no overlap and no aliasing of current slots with Apple ROM.

For each supported card slot `N ∈ {1,2,4,5,6,7}`:

- Each slot array remains exactly 4096 bytes; destination `N << 12`.
- Apple `$Cn00–$CnFF` = slot image offsets `0x000–0x0FF` (**256-byte IOSEL**).
- Offsets `0x100–0x7FF` = padding / future, preserved from compiled array (default zero).
- Apple `$C800–$CFFF` = selected slot image offsets `0x800–0xFFF` (**2048-byte IOSTB**, including CFFF).
- After a CFFF read or write, the selector releases for the **next** cycle, not during its returned data byte; slot 0 fallback is zero. The Apple internal `$C800` selection is a separate MMU case.
- Built-in Apple internal `$C300`, `$C600` and other Cx bytes remain at physical `0x0C300`, `0x0C600`, etc., **not** copied into card slots. External slot 6 uses `0x06000` independently.

**Explicitly preserve** the existing `#ifndef SLOT1_ROM`, `SLOT2_ROM`, `SLOT4_ROM`, `SLOT5_ROM`, `SLOT6_ROM`, `SLOT7_ROM` guards, their `slotN_rom_bin[]` symbols, and compile-time 4 KiB assertions. No slot 0 or slot 3 array should be added.

## 2. Device facts and hardware compatibility

**Selected electrical device family:** `SST39VF010-70`, a 1 Mbit, 128K × 8, **70 ns**, parallel NOR flash with address inputs **A0–A16**, data **DQ0–DQ7** and active-low **CE#**, **OE#**, **WE#**. A16 selects the unused/upper 64 KiB and is **not needed for any current CPU-ROM read**.

Microchip DS20005023E lists PLCC32 (`-NHE`) and TSOP32 (`-TU`) for
this family. Confirm the complete purchase part number, including suffix.
A DIP32 socket requires a pin-mapped PLCC32 or TSOP32 adapter and verified
orientation, or an owner-approved footprint change.

**Voltage and timing are blocking physical-hardware gates.** This is a **low-voltage flash** (nominal **3.3 V**, VF variant documented 2.7–3.6 V in datasheet features/AC and distributor listings; verify the exact purchased suffix and latest datasheet before fabrication). It is **not a 5 V-powered ROM**. Normal pin stress limits are `-0.5 V` to `VDD+0.5 V` (datasheet has a special A9 allowance; do not treat that as general 5 V tolerance). The Apple IIe CPU/legacy bus and any 5 V CPLD signals must **not** drive the flash address/control pins directly at 5 V. Design 5 V→3.3 V translation or verified 3.3 V drive for **all** address and enable inputs; verify the **3.3 V→Apple-side DQ output** meets the actual CPU/CPLD VIH and bus driver requirements, adding a suitable buffered level translator if necessary. Respect bus direction and high-Z timing. Provide a regulated 3.3 V rail and bypassing. Document rail sequencing and avoid flash back-power through interface pins.

**Read timing:** `tAA` address and `tCE` chip-enable access **70 ns max**, `tOE` **35 ns max**, and `tCHZ`/`tOHZ` disable-to-high-Z **25 ns max** (per Microchip DS20005023 timing table for the VF-70). Verify the actual CPU/PHI_0 data setup/hold, address mux and level-translator propagation margins; 70 ns on a datasheet **does not itself prove timing closure**. Recommended power-up-to-read delay is 100 µs. On target, this flash is **read-only**: `WE#` must be held safely high at the flash VDD (not switched with CPU R/W); programming happens outside the target or through an explicitly isolated future programming interface. `CE#` and `OE#` must be asserted only for authorised ROM read cycles, released during RAM/I/O/writes/reset where appropriate, and tri-stated before any competing device drives data. `C6XX_N` can assert during internal or external slot6 cases; resolve actual bus owner rather than blindly OR-ing chip enables.

The reference design straps A16 to flash VSS and leaves the RAM bank line
separate. The hardware ticket lists all PLCC32 and TSOP32 pins and the
timing and arbitration requirements.

## 3. RTL and CPLD/ROM address-bus work

**Preferred scope: no functional ROM RTL change unless tests uncover a specific failure.** The current approved MMU already routes ROM addresses into **the lower 16 bits**:

- In `rtl_MMU/MMU_addr.v`: on `rom_enabled`, `mem_addr_upper = {1'b0, ADDR[15:12]}`. On card `slot_rom_read`, `mem_addr_upper = {2'b00, slot_index}`. Therefore the combined ROM physical address has **A16=0**; the upper 64 KiB remains unreachable as ROM. In contrast, **RAM banking may use address bit 16**; do not conflate RAM and ROM output semantics.
- For card IOSEL, the lower address is `{4'd0, ADDR[7:0]}`; for card IOSTB and Apple ROM it is `ADDR[11:0]`. The default hardware interface exposes only `MEM_ADDR_OUT[16:12]`; `cpld/rtl_interconnect.cpp` reconstructs A11–A0 according to the strobes. The real PCB/CPLD logic must reproduce the same selection. Do not feed the CPU's A11–A8 directly to the card IOSEL ROM location without zeroing them.
- On actual target, drive or strap flash **A16 low on all current ROM accesses**; reserve A16 as an option for a *future approved bank controller*. A 0-ohm/jumper/selectable strap or explicit controlled output may be documented, but **no automatic high-bank mirroring, bank switching or hidden dependence on RAM aux-bank bit16** is allowed now.
- Review `MODE_SEL` 0/1 decode, `ROM_EN_N`, `IOSEL_N`, `IOSTB_N`, `C6XX_N`, `CPU_RW`, `RAM_EN_N`, slot3 internal Cx ownership and CFFF release. `ROM_EN_N` alone is **not sufficient to identify every external card ROM read** under the emulator/RTL design. The physical flash CE#/OE# equations must handle the complete authorised read set and avoid accidental overlap with external slot6 or IOU I/O devices.
- If PCB pin count or present RTL interface cannot implement the 12 low-address bits and ROM/card enables, write a **specific** hardware/interface gap and a failing simulation before proposing functional RTL changes. Do not alter RAM address banking or rewrite the approved MMU merely because the storage device is now 128 KiB.
- Explicitly state whether there is any physical signal to gate A16. With a fixed A16-low strap, **all high-bank reads are impossible**, by design; the upper 64 KiB's file contents are reserved, not addressable hardware features.
